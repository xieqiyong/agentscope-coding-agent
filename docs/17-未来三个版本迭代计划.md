# 未来三个版本迭代计划

这份文档记录多 Agent 后续 1 到 3 个版本的演进规范。

当前项目已经具备本地多 Agent 编排骨架、自定义 Agent、计划卡片、步骤执行和基础 `AgentGraph`。下一阶段不要急着引入完整 LangGraph Runtime 或 Nacos 体系，优先把本地调度器、状态恢复、验证闭环和前端可观测体验做稳。

## 总体判断

建议路线：

```text
V1：Multi-Agent Scheduler + Harness Agent
V2：协作看板 + Reviewer / Repair Loop
V3：A2A + Nacos + 远程 Agent 注册发现
```

LangGraph 的思想要吸收，但不建议现在直接接入它的运行时。

原因：

- 项目主栈是 Java + Spring Boot + AgentScope Java。
- 直接引入 Python / JS 图运行时会增加状态同步、事件流、工具治理和部署复杂度。
- 当前最缺的是稳定调度、可恢复状态和验证闭环，不是更多外部框架。

因此短期目标是把自己的 `AgentGraph` 做成类似 LangGraph 的 Java 编排抽象：

```java
graph.addNode("planner", plannerNode);
graph.addNode("frontend", frontendAgentNode);
graph.addNode("backend", backendAgentNode);
graph.addNode("harness", harnessAgentNode);
graph.addEdge("planner", "frontend");
graph.addEdge("planner", "backend");
graph.addEdge("frontend", "harness");
graph.addEdge("backend", "harness");
graph.addConditionalEdge("harness", state -> state.success() ? "reviewer" : "repair");
```

## 通用开发规范

后续版本都要遵守这些约束：

- 新增后端接口默认全部使用 `POST`。
- Java 注释统一使用中文。
- Service 依赖注入使用 `@Resource` 或 `@Autowired`，不要使用构造器注入或 Lombok 构造器注入。
- DDD 分层遵守：`domain` 零框架依赖，框架代码只允许出现在 `infrastructure` 或外层适配模块。
- AgentScope 只负责 Agent Loop，平台负责 workspace、状态、调度、记忆、工具治理、持久化和前端状态。
- 所有 Agent 执行必须落事件，前端状态不能只依赖内存临时变量。
- 任何任务图、计划步骤、工具调用和验证结果都要支持刷新恢复。
- 先做本地可恢复调度，再做远程 Agent 注册发现。

## V1：Multi-Agent Scheduler + Harness Agent

目标：让多 Agent 不只是“计划卡片”，而是可以被平台稳定调度、暂停、继续、取消和验证。

### 核心能力

- 将计划从线性 `List<AgentPlanStep>` 升级为 `TaskGraph`。
- 新增 `MultiAgentScheduler`，统一负责节点调度。
- 支持串行执行、依赖执行、失败中断、取消运行。
- 新增 `Harness Agent`，专门负责构建、检查、验证和回传错误。
- 每个任务节点绑定明确执行上下文：
  - `nodeId`
  - `agentId`
  - `agentRole`
  - `modelConfigId`
  - `status`
  - `input`
  - `output`
  - `startedAt`
  - `finishedAt`
  - `errorMessage`

### Harness Agent 职责

Harness Agent 不是业务专家，不负责写业务代码。

它只做验证：

- 查看当前 diff。
- 执行后端编译，例如 `mvn -q -DskipTests compile`。
- 执行前端构建，例如 `npm run build`。
- 检查是否修改了 workspace 外路径。
- 检查是否出现明显编译错误、类型错误、依赖缺失。
- 输出结构化验证报告。
- 验证失败时，把失败原因交还给对应专家 Agent 修复。

### 后端改造点

- 新增 `TaskGraph`、`TaskNode`、`TaskEdge`、`TaskNodeStatus`。
- 新增 `MultiAgentScheduler`。
- 将 `MultiAgentOrchestrator` 从“直接执行流程”收敛为“创建图 + 触发调度”。
- 为每个节点记录事件：
  - `TASK_NODE_CREATED`
  - `TASK_NODE_STARTED`
  - `TASK_NODE_FINISHED`
  - `TASK_NODE_FAILED`
  - `TASK_GRAPH_CANCELLED`
- 会话 timeline 恢复时重建任务图和节点状态。

### 前端改造点

- 计划卡片支持任务图节点状态。
- 增加“执行下一步”“暂停”“继续”“取消”。
- 每个步骤展示负责 Agent 和模型配置。
- Harness 验证结果用独立区块展示。

### 验收标准

- 刷新页面后，计划卡片和步骤状态不丢失。
- 点击取消后，后端 run 和前端 UI 都进入 `CANCELLED`。
- Harness 验证失败时，能在 UI 看到失败命令、错误摘要和关联节点。
- 同一张计划卡片不会重复执行同一个已完成节点。

## V2：协作看板 + Reviewer / Repair Loop

目标：让前端专家、后端专家、架构师、Reviewer 可以围绕同一个任务协作，并且能看到彼此进度。

### 核心能力

- 新增多 Agent 协作看板。
- 支持并行节点执行。
- 新增 `ReviewerAgent`，负责审查 diff、验证结果和实现一致性。
- 新增 `Repair Loop`，验证失败时自动路由回对应专家 Agent。
- 支持每个 Agent 独立模型配置和最大迭代次数。

### 推荐流程

```text
用户任务
  ↓
PlannerAgent 生成 TaskGraph
  ↓
ArchitectAgent 约束方案和边界
  ↓
FrontendAgent / BackendAgent 并行执行
  ↓
HarnessAgent 验证构建和基础检查
  ↓
ReviewerAgent 汇总审查
  ↓
Finalizer 生成最终回复
```

失败时：

```text
HarnessAgent 验证失败
  ↓
Scheduler 定位失败节点
  ↓
回到对应 FrontendAgent / BackendAgent
  ↓
修复后再次进入 HarnessAgent
```

### 后端改造点

- `TaskGraph` 支持并行 ready queue。
- `Scheduler` 支持最大并发数控制。
- 增加节点重试次数和失败策略：
  - `FAIL_FAST`
  - `RETRY_THEN_FAIL`
  - `ROUTE_TO_REPAIR`
- 增加 Reviewer 节点协议：
  - 输入：任务目标、计划、diff、工具调用摘要、Harness 报告。
  - 输出：是否通过、问题列表、修复建议、最终摘要。

### 前端改造点

- 新增协作看板视图。
- 每个 Agent 显示：
  - 当前节点
  - 当前状态
  - 使用模型
  - 最近工具调用
  - 输出摘要
- 任务图展示依赖关系和执行进度。
- 支持展开单个 Agent 的执行日志。

### 验收标准

- 前端和后端专家可以并行处理不同节点。
- Reviewer 可以基于 diff 和 Harness 报告输出审查结果。
- 失败节点可以回到对应专家修复，而不是整轮任务重跑。
- 用户能清楚看到每个 Agent 当前进度。

## V3：A2A + Nacos + 远程 Agent 注册发现

目标：把本地多 Agent 编排升级为可分布式扩展的 Agent 调度平台。

这一版再引入 Nacos 更合适。

在 V1/V2 之前不建议引入 Nacos，因为当前 Agent 还在同一个进程内，过早做注册发现只会增加复杂度。

### 什么时候需要 Nacos

满足以下条件时再接入：

- Agent 分布在多个服务实例。
- 不同机器运行不同专家 Agent。
- 需要动态注册 Agent 能力。
- 需要 Agent 心跳、上下线和负载均衡。
- 需要跨进程或跨机器调用 Agent。

### 核心能力

- 定义平台内部 A2A 协议。
- Agent 能力注册到 Nacos。
- Scheduler 根据能力、负载和可用性选择 Agent。
- 支持远程 Agent 调用、心跳和失败转移。
- 支持本地 Agent 与远程 Agent 混合编排。

### A2A 协议最小字段

```json
{
  "taskId": "task-001",
  "nodeId": "backend-001",
  "conversationId": 1,
  "workspaceId": 1,
  "agentRole": "BACKEND",
  "input": "实现接口",
  "constraints": [],
  "contextRefs": [],
  "expectedOutputSchema": {}
}
```

返回：

```json
{
  "taskId": "task-001",
  "nodeId": "backend-001",
  "status": "COMPLETED",
  "summary": "已完成接口实现",
  "artifacts": [],
  "events": [],
  "errorMessage": null
}
```

### Nacos 注册信息

建议每个 Agent 实例注册这些能力：

```text
agentId
agentName
agentRole
skills
mcpServices
modelProvider
modelName
maxConcurrency
workspaceAccessMode
healthStatus
lastHeartbeatAt
```

### 后端改造点

- 新增 `AgentRegistry` 抽象。
- 新增 `LocalAgentRegistry`，保持当前本地 Agent 能力。
- 新增 `NacosAgentRegistry`，接入 Nacos 服务发现。
- 新增 `RemoteAgentClient`，负责远程 Agent 调用。
- Scheduler 从 Registry 查询候选 Agent。
- 所有远程调用必须记录事件和审计日志。

### 前端改造点

- Agent 页面展示本地 Agent 和远程 Agent。
- 展示 Agent 在线状态、负载、能力标签。
- 编排看板区分本地执行和远程执行。

### 验收标准

- 本地 Agent 和远程 Agent 可以被统一选择。
- 远程 Agent 下线后，Scheduler 不再分配新任务。
- 远程执行失败能反馈到当前任务图。
- 不接 Nacos 时，本地模式仍然完整可用。

## LangGraph 的位置

短期不直接引入 LangGraph Runtime。

可以保留三个方向：

1. 学习它的设计语言：`State`、`Node`、`Edge`、`ConditionalEdge`、`Checkpoint`、`Interrupt`。
2. 在 Java 内部实现兼容思想的 `AgentGraph` 和 `TaskGraph`。
3. 未来如果要接 Python Agent 生态，可以做一个 `LangGraphRemoteAgent`，通过 A2A 协议调用，而不是把 Python Runtime 塞进主后端。

## 非目标

未来三个版本暂时不做：

- 不做完整低代码工作流编辑器。
- 不做面向生产的强隔离沙箱。
- 不做跨租户 SaaS 权限体系。
- 不做完整 Agent Marketplace。
- 不做复杂回滚系统。

这些能力可以在 Scheduler、A2A 和远程沙箱稳定后再考虑。

## 推荐实施顺序

```text
1. TaskGraph 数据结构
2. TaskGraph 事件持久化
3. MultiAgentScheduler
4. Harness Agent
5. 计划卡片节点状态恢复
6. Reviewer Agent
7. Repair Loop
8. 协作看板
9. LocalAgentRegistry
10. NacosAgentRegistry
11. RemoteAgentClient
12. A2A 协议稳定化
```

核心原则：

```text
先调度，再分布式。
先验证，再自动修复。
先本地 Registry，再 Nacos。
先事件恢复，再复杂 UI。
先跑通 Harness，再扩大 Agent 数量。
```
